# Rig-only hardware integration test

Run only on the rs-vm-37 emulator/Bumble rig with the real Jetson using `/root/rig/run-hil.sh` in a detached `systemd-run` owner. The runner owns one `jetson-hil.sh session`, installs the dev-flavor debug APK, checks the privileged pairing agent, and collects evidence before powering off and returning `hci0` to BlueZ. Do not run this test in CI or on a phone: it uses the rig Ethernet address `10.10.1.30` and the local RTMP receiver `10.10.1.37`.

The test is deliberately under `integration_test/hil/`, not `test/`: plain `just test` (`flutter test`) and `just ci` discover `test/` only. Invoke explicitly with `flutter test integration_test/hil -d emulator-5554 --flavor dev --dart-define=APP_ENV=dev --dart-define=EMULATE=false --dart-define=SEED=false --dart-define=HIL_RTMP_URL=rtmp://10.10.1.37:1935/p14a/ingest`. For a Jetson-off harness check, add `--dart-define=HIL_OFFLINE=true`; the scan must fail with a bounded timeout. The production app and services are unchanged: the test overrides only `wifiServiceProvider` to route preview and the token-authenticated HTTP download to Ethernet, while retaining the real BLE implementation. Native pairing is handled by the rig's privileged agent, not by taps.

A passing test is not by itself hardware sign-off: the runner waits for the firmware's BLE advertisement before booting the emulator, verifies the shutdown summary against the second match ID, and requires nonzero RTMP receiver inbound bytes before stopping the service. The second session is blocked by firmware resetting its connected session to Idle after the first finalization; do not bypass this with a test reconnect. Recording/streaming are direct real BLE command-path checks; only scan/connect/preview use app widgets. The current session does not test the match setup, end-of-match, or download-sheet UI. Bridge excerpts are filtered; never publish raw BLE bridge logs or credentials.
